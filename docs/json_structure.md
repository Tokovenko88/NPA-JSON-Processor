# ТЕХНИЧЕСКАЯ ДОКУМЕНТАЦИЯ: ОПИСАНИЕ СТРУКТУРЫ JSON НПА (ВЕРСИЯ С ПОДДЕРЖКОЙ ИСТОРИИ НОМЕРОВ И ДУБЛЕЙ)

Данный JSON-формат предназначен для цифрового представления структуры нормативно-правовых актов (НПА), в частности постановлений Законодательного Собрания города Севастополя и Законов города Севастополя.  
Он позволяет точно описать иерархию документа, типы его структурных элементов и их взаимосвязи, что делает его идеальным для создания электронных библиотек, систем поиска и аналитических инструментов.

**Версия формата** включает поддержку версионирования номеров элементов (`number_revisions`) для корректной обработки дублирующихся номеров (ошибок законодателя) и их последующих исправлений без изменения `item_id`.  
Для явного обозначения дублей в `item_id` добавляется суффикс `_double_N`.

## 1. КОРНЕВОЙ ОБЪЕКТ: ПАСПОРТ НПА

Содержит метаданные и глобальные константы документа.

- **npa_id** (число, обязательно)  
  Уникальный ID, привязанный к базе данных Сайта.

- **npa_type** (строка, обязательно)  
  Тип документа: `regulation` — постановление, `law` — закон.

- **npa_number** (строка, обязательно)  
  Официальный регистрационный номер документа.

- **npa_author** (строка, обязательно)  
  Субъект законодательной инициативы.

- **npa_npa_committee** (строка, опционально)  
  Ответственный комитет (комиссия).

- **pub_info** (строка, опционально)  
  Информация об источнике опубликования для законов (law), если номер закона меньше 176.

- **pub_filepath** (строка, опционально)  
  Полный путь к образу опубликованного документа на сайте Законодательного Собрания sevzakon.ru. Используется для законов с номером больше 175 и для постановлений при наличии.

- **npa_url** (строка, обязательно)  
  Полный URL-адрес текста НПА на сайте Законодательного Собрания.

- **date_reg** (строка, обязательно)  
  Дата регистрации проекта НПА в формате `d.m.Y`.

- **date_cons** (строка, опционально)  
  Дата подготовки НПА в формате `d.m.Y`.

- **date_1st_reading** (строка, обязательно для `law`, для `regulation` отсутствует)  
  Дата рассмотрения Закона в первом чтении в формате `d.m.Y`.

- **date_passed** (строка, обязательно)  
  Дата принятия НПА в формате `d.m.Y`.

- **date_signed** (строка, опционально)  
  Дата подписания закона в формате `d.m.Y` (только для законов).

- **date_pub** (строка, обязательно)  
  Дата официальной публикации НПА в формате `d.m.Y`.

- **valid_from** (строка, обязательно)  
  Дата вступления документа в силу в формате `d.m.Y`. Служит точкой отсчета для версий.

- **not_valid** (строка, опционально)  
  Дата утраты законом силы в формате `d.m.Y`.

  - **not_valid_npa** (строка, опционально)  
  ID НПА, который вызвал утрату силы.

- **npa_signer_post** (строка, обязательно)  
  Официальная должность лица, подписавшего документ.

- **npa_signer** (строка, обязательно)  
  Фамилия и инициалы подписанта.

- **term_number** (строка, опционально)  
  Номер созыва римскими цифрами (для постановлений).

- **session_number** (строка, опционально)  
  Номер сессии римскими цифрами (для постановлений).

- **date_format** (число, обязательно)  
  Числовой код, определяющий формат отображения дат для обеспечения исторической аутентичности.

- **not_valid_note** (строка, опционально)  
  Ссылочный идентификатор (ID элемента), послужившего причиной утраты силы.

- **npa_notes** (массив объектов, опционально)  
  Справочная информация по всему НПА. Каждый элемент массива — пара из текста и даты, определяющей срок актуальности этой информации.  
  Структура объекта:
  - `text` (строка, обязательно) — текст примечания.
  - `valid_from` - (строка, обязательно) — дата в формате `d.m.Y`, определяющая срок начала действия зпримечания
  - `valid_to` (строка, необязательно) — дата в формате `d.m.Y`, до которой данная справочная информация считается актуальной, если не указана - бессрочно.
 
 Пример (запись в JSON): `"npa_notes": [ { "text": "По данному Закону имеется Севастопольского городского суда от 27.12.2017 ", "valid_from": "01.01.2025",  "valid_to": "" } ]`


  Пример (запись в JSON): `"npa_notes": [ ]`

- **no_name** (строка, опционально)  
  Перечень ID структурных элементов (через запятую), для которых у разделов (`section`) отсутствует служебное слово «Раздел».  
  Примеры:  
  `"123"` — правило действует для всего корневого документа (npa_id = 123);  
  `"123,123_appendix_6_double_1"` — правило действует для корневого документа и для приложения с item_id = 123_appendix_6_double_1.

- **head_revision** (массив объектов, обязательно)  
  Содержит историю заголовков НПА. Каждый объект включает поля:
  - `npa_head` (строка) — текст наименования,
  - `modified_by_id` (строка) — список ID элементов через запятую, которые инициировали данное изменение,
  - `valid_to` (строка) — дата окончания действия конкретной редакции наименования,
  - `highlights` (объект, опционально) — информация о подсветке изменений (добавления, удаления, замены) для отображения разницы между редакциями.

- **npa_items_revision** (массив объектов, обязательно)  
  Корневой массив, содержащий все структурные элементы верхнего уровня.

- **revision_info** (массив объектов, опционально)  
  Содержит информацию о документах, вносящих изменения. Описание элемента см. в разделе 4.

## 2. СТРУКТУРНЫЙ ЭЛЕМЕНТ (УЗЕЛ ДЕРЕВА)

Каждый объект внутри массивов `npa_items_revision` и `item_children` представляет собой узел дерева (статью, главу, раздел, пункт, таблицу со структурой и т.д.).

- **item_id** (строка, обязательно)  
  Уникальный идентификатор, формируемый по строгому шаблону:  
  `<npa_id>_<type>_<number>_<double_N>`,  
  где `_double_N` добавляется только для дублирующихся элементов (начиная с N=1).  
  Для недублирующихся элементов суффикс опускается.  
  Для элементов внутри `structured_table` добавляется префикс с номером таблицы.  
  **Важно:** При последующем изменении номера элемента (например, исправлении дублирующегося номера с `"5"` на `"5.1"`) поле `item_id` **не меняется**.  
  Уникальность идентификаторов при изначальном дублировании номеров обеспечивается добавлением `_double_N` (например, `123_article_5_double_1` и `123_article_5_double_2`).  
  Это гарантирует стабильность всех ссылок (`child_ref`, `modified_by_id`, `not_valid`).

- **item_type** (строка, обязательно)  
  Семантическая роль элемента. Допустимые значения:  
  `preamble`, `chapter`, `section`, `article`, `part`, `point`, `subpoint`, `appendix`, `nested_appendix`, `structured_table`.

- **item_number** (строка, опционально)  
  **Текущий** номер элемента. Если `number_revisions` отсутствует, это единственный номер.  
  При наличии `number_revisions` поле `item_number` всегда должно содержать номер из последней действующей редакции (объект с наибольшей датой `valid_from` и отсутствующим `valid_to`).  
  Используется для быстрого доступа к актуальному номеру без разбора массива ревизий.

- **item_level** (число, обязательно)  
  Числовой показатель уровня вложенности (1 для элементов верхнего уровня, для каждого вложенного дочернего элемента увеличивается на 1).

- **item_notes** (массив объектов, опционально)  
  Справочная информация, специфичная для данного узла. Каждый элемент — пара из текста и даты актуальности.  
  Структура объекта:
  - `text` (строка, обязательно) — текст примечания.
  - `valid_from` - (строка, обязательно) — дата в формате `d.m.Y`, определяющая срок начала действия зпримечания
  - `valid_to` (строка, необязательно) — дата в формате `d.m.Y`, определяющая срок актуальности данной информации, если не указана - бессрочно.

    Пример (запись в JSON): `"item_notes": [ { "text": " Действие положений статьи 3 распространяются на правоотношения, возникшие с 7 июля 2023 года", "valid_from": "01.08.2023",  "valid_to": "" } ]`

- **item_prefix_revisions** (массив, опционально)  
  Версии служебной информации перед названием приложения. Каждый объект содержит:  
  `prefix_text`, `valid_from`, `valid_to`, `mod_type`, `modified_by_id`, `highlights`, `not_valid`.

- **item_children** (массив объектов, опционально)  
  Содержит дочерние элементы той же структуры.

- **head_revisions** (массив объектов, опционально)  
  Массив версий заголовков для глав, разделов, статей, приложений и структурированных таблиц. Каждый объект содержит:  
  `head_text`, `valid_from`, `valid_to`, `mod_type`, `modified_by_id`, `highlights`.

- **number_revisions** (массив объектов, опционально)  
  **История изменений номера элемента.** Позволяет зафиксировать ситуацию, когда законодатель ошибочно присвоил двум элементам одинаковый номер, а затем исправил один из них, или любые другие случаи изменения нумерации.  

  Каждый объект массива содержит следующие поля:

  - `number_text` (строка, обязательно)  
    Номер элемента в данной версии (например, `"5"`, `"5.1"`, `"а"`, `"I"`).

  - `valid_from` (строка, обязательно)  
    Дата начала действия этого номера в формате `d.m.Y`.

  - `valid_to` (строка, опционально)  
    Дата окончания действия номера. Если отсутствует — номер действует бессрочно. Для предыдущих версий номеров поле обязательно.

  - `mod_type` (строка, опционально)  
    Тип изменения: `"correction"` (исправление ошибочного дублирования), `"renumber"` (плановая перенумерация), `"editorial"` (редакционная правка).

  - `modified_by_id` (строка, опционально)  
    `item_id` документа (НПА), которым внесено данное изменение номера.

  - `highlights` (объект, опционально)  
    Подсветка изменений номера (аналогично `highlights` в `head_revisions` и `revisions`).

  - `not_valid` (строка, опционально)  
    `item_id` документа, отменившего действие данной версии номера.

  **Правила использования:**
  - Если номер элемента никогда не изменялся, массив `number_revisions` отсутствует (рекомендуемый способ) или содержит единственный объект. В этом случае `item_number` хранит текущий номер.
  - При первом изменении номера добавляется новый объект в `number_revisions`, при этом предыдущий объект получает `valid_to = дата_начала_действия_нового_номера - 1 день`.
  - Поле `item_number` **обязательно** синхронизируется с последним действующим объектом в `number_revisions` (если массив существует).
  - `item_id` остаётся неизменным на протяжении всего жизненного цикла элемента, что гарантирует корректную работу ссылок из других элементов (`child_ref`, `modified_by_id`, `not_valid`).

- **revisions** (массив объектов, обязательно)  
  Хранит историю редакций контента элемента. Каждый объект содержит:  
  `valid_to`, `valid_from`, `modified_by_id`, `mod_type`, `body` (массив блоков контента), `highlights`, `not_valid`.

### Особенности элемента `structured_table`

- Не отображается в оглавлении документа и не имеет собственного якоря для навигации. Его дочерние элементы (`section`, `point`, `subpoint`) отображаются в оглавлении как обычно.
- Содержимое формируется из блоков в `body`: `paragraph`, `table_header`, `child_ref`.
- Дочерние элементы в своих `revisions[].body` содержат блоки `table_fragment` с HTML-кодом строк таблицы.

## 3. КОНТЕНТНЫЙ БЛОК (BODY)

Массив `body` внутри редакции элемента позволяет чередовать текст, таблицы, ссылки на дочерние элементы, а также специальные блоки для структурированных таблиц.

### 3.1. Базовые типы блоков

- **paragraph**  
  Поля: `html_text` (строка), `order` (число).

- **table**  
  Поля: `html_text` (полный HTML-код таблицы), `order`.

- **child_ref**  
  Поля: `item_id` (строка), `order`.

### 3.2. Специальные блоки для структурированных таблиц

- **table_header**  
  Используется только внутри `structured_table`. Поля: `html_text` (содержимое `<thead>`), `order`.

- **table_fragment**  
  Используется только в `revisions[].body` дочерних элементов `structured_table`. Поля: `html_text` (одна или несколько строк `<tr>`), `order`.

## 4. СПИСОК ИЗМЕНЯЮЩИХ ДОКУМЕНТОВ (REVISION_INFO)

Каждый объект в массиве `revision_info` описывает один документ, вносивший правки в текущий НПА. Поля:

- `revision_id` (строка, обязательно) — уникальный идентификатор изменяющего документа.
- `revision_number` (строка, обязательно) — официальный регистрационный номер.
- `revision_date_reg` (строка, обязательно) — дата регистрации.
- `revision_date_valid` (строка, обязательно) — дата вступления в силу изменений.
- `revision_url` (строка, опционально) — ссылка на текст изменяющего документа.

## 5. ОБЪЕКТ HIGHLIGHTS (ПОДСВЕТКА ИЗМЕНЕНИЙ)

Используется в редакциях заголовков и контента для отображения разницы между версиями документа. Поддерживает два независимых режима разметки: текстовый и табличный.

### 5.1. Текстовый режим (для обычных абзацев и текстовых блоков)

- `text` (строка) — конкретное измененное, добавленное или удаленное слово/фраза.
- `positions` (строка) — координаты вхождений вида `"M-N"`, где `M` — порядковый номер абзаца в элементе, а `N` — порядковый номер вхождения этой фразы в абзаце (слева направо).

### 5.2. Табличный режим (для изменения строк таблицы целиком)

Применяется при любых модификациях табличных данных, затрагивающих строки таблицы (`<tr>`) целиком. Подсветка отдельных слов внутри ячеек не производится, контент ячеек в объект разницы не передается.

- `text` (строка) — СТРОГО фиксированное служебное слово `"table"`.
- `positions` (строка) — порядковые номера измененных, удаленных или добавленных строк (тегов `<tr>`) внутри модифицируемой таблицы через запятую. Нумерация строк 1-базовая, сквозная сверху вниз.

**Критическое правило замен (difference):** Замена строк всегда строго попарная. Массивы `previous_edition.difference` и `current_edition.difference` обязаны иметь одинаковое количество элементов. Каждая независимая замена строки (или непрерывного блока строк) должна записываться отдельным изолированным объектом в массивах, чтобы элемент с индексом `[i]` в старой редакции четко соответствовал элементу `[i]` в новой редакции.

Пример структуры объекта с табличной подсветкой (построчная замена строк 2 и 3):

previous_edition:  
- deletion: []  
- difference: [ { text: "table", positions: "2" }, { text: "table", positions: "3" } ]  

current_edition:  
- addition: []  
- difference: [ { text: "table", positions: "2" }, { text: "table", positions: "3" } ]  

## 6. ПРИМЕР ИСПОЛЬЗОВАНИЯ NUMBER_REVISIONS ДЛЯ ИСПРАВЛЕНИЯ ДУБЛИРУЮЩЕГОСЯ НОМЕРА

Исходный НПА (оба элемента ошибочно имеют номер "5"):

Объект 1:  
item_id: "123_article_5", item_type: "article", item_number: "5", item_level: 1, revisions: [ ... ]  

Объект 2:  
item_id: "123_article_5_double_1", item_type: "article", item_number: "5", item_level: 1, revisions: [ ... ]

После принятия корректирующего НПА, который меняет номер второго элемента на "5.1" с 15.03.2025, объект 2 модифицируется:

item_id: "123_article_5_double_1" (не изменился)  
item_type: "article"  
item_number: "5.1"  
item_level: 1  
number_revisions:  
- номер версии 1: number_text: "5", valid_from: "01.01.2024", valid_to: "14.03.2025"  
- номер версии 2 (текущая): number_text: "5.1", valid_from: "15.03.2025", mod_type: "correction", modified_by_id: "456_correction_law", highlights: { ... }  

Первый элемент остаётся без изменений (номер "5", item_id = "123_article_5").

Благодаря такому подходу:
- Все ссылки, указывавшие на 123_article_5_double_1, продолжают работать.
- При отображении на дату 01.02.2024 оба элемента показывают номер "5"; на дату 01.04.2025 первый — "5", второй — "5.1".
- Ошибка законодателя корректно зафиксирована в истории.

## 8. ЗАМЕЧАНИЯ ПО ОБРАБОТКЕ ТАБЛИЦ

- Если таблица не содержит структурных элементов — она представляется как обычный блок `table`.
- Заголовок таблицы (центрированный) не должен быть ошибочно принят за заголовок приложения.
- Префикс (например, «тыс. руб.») сохраняется как блок `paragraph` внутри `structured_table`.
- Шапка таблицы (`<thead>`) может отсутствовать.
- При версионировании изменения в таблице создают новую редакцию родительского элемента, а старые редакции сохраняются. Все изменения структуры строк таблицы (добавление, удаление, замена `<tr>`) используют исключительно табличный режим объекта highlights со служебным словом `"table"`.

## 9. ПРАВИЛА ПОСТРОЕНИЯ ИЕРАРХИИ ВНУТРИ STRUCTURED_TABLE

Для элемента типа `structured_table` действуют строгие ограничения на допустимые типы дочерних элементов и алгоритм распознавания строк таблицы как структурных единиц.

### 9.1. Допустимая иерархия вложенности

Внутри `structured_table` может использоваться только следующая последовательность типов элементов (в порядке увеличения уровня вложенности):
- `section` — раздел таблицы (необязательный уровень, может отсутствовать)
- `point` — пункт таблицы
- `subpoint` — подпункт таблицы
- `subpoint` более низкого уровня (допускается многократное вложение subpoint)

Уровень вложенности (`item_level`) возрастает на 1 для каждого вложенного типа.  
Запрещено использовать: `chapter`, `article`, `part`, `appendix`, `nested_appendix`, `preamble`, `structured_table` внутри другой `structured_table`.

### 9.2. Алгоритм поиска признака структурного элемента при парсинге

При преобразовании исходной HTML-таблицы в структурированное представление каждая строка таблицы (элемент `<tr>`) анализируется по следующим правилам:

#### 9.2.1. Определение раздела таблицы (section)

Строка считается разделом, если первая ячейка строки (`<td>`) содержит текст, начинающийся со слова «Раздел» (без учёта регистра, но с сохранением оригинального написания).  
Обязательное условие: строка должна состоять ровно из одной ячейки (допускается `colspan`, но ячейка должна занимать всю ширину таблицы).  
Внутри этой единственной ячейки могут присутствовать номер раздела и наименование.  
Если строка содержит более одной ячейки или первая ячейка не начинается со слова «Раздел» — строка не может быть распознана как раздел.

Пример корректного раздела:  
`<tr><td colspan="2"><strong>Раздел 1. Общие положения</strong></td></tr>`

#### 9.2.2. Определение пунктов, подпунктов и их вложенности

Пункт (`point`) или подпункт (`subpoint`) распознаётся исключительно по началу содержимого первой ячейки строки.  
Если первая ячейка строки начинается с:
- цифры с точкой (например, `1.`, `2.3.`),
- римской цифры с точкой или скобкой (`I.`, `II.`),
- буквы с точкой или скобкой (`а.`, `б`),
- любого другого явного нумератора, который в документе используется для обозначения пункта/подпункта,
то такая строка считается структурным элементом (`point` или `subpoint`).

В противном случае (первая ячейка начинается с произвольного текста без нумератора) — вся строка обрабатывается как неструктурированный элемент и помещается в блок `paragraph` (или `table_fragment` без привязки к `item_id`), но не порождает отдельный объект `point`/`subpoint`.

#### 9.2.3. Определение уровня вложенности

Уровень вложенности (`item_level`) для пунктов/подпунктов определяется по количеству разделителей в нумераторе (точки, скобки) или по визуальному отступу.  
Рекомендуется:
- `1.` или `а)` — уровень 1 (если нет родительского раздела) или уровень 2 (если есть раздел);
- `1.1.` или `а)` внутри пункта — уровень 2 (подпункт);
- `1.1.1.` — уровень 3 и т.д.

Приоритет имеет фактическая вложенность в массиве `item_children`: если элемент `point` уже имеет дочерние `subpoint`, то нумератор дочерних элементов должен логически соответствовать их положению.

#### 9.2.4. Пример обработки строк таблицы

- Строка с текстом «Раздел 2. Доходы бюджета» в единственной ячейке, охватывающей все колонки, распознаётся как `section`.
- Строка, где первая ячейка содержит «1.1.» и далее идут другие ячейки со значениями, распознаётся как `point`.
- Строка, где первая ячейка начинается с «а)», распознаётся как `subpoint`.
- Строка с пояснительным текстом без нумератора (например, «Пояснительный текст») не является структурным элементом и помещается в `table_fragment`.

### 9.3. Последствия для версионирования и рендеринга

- Если строка не удовлетворяет правилам `section`, `point` или `subpoint`, её HTML остаётся внутри `table_fragment` родительского элемента как обычный текст — без возможности независимого версионирования.
- Добавление, удаление или изменение нумератора у строки, которая ранее была распознана как структурный элемент, требует создания новой редакции соответствующего элемента (`point`/`subpoint`) и его родителя.
- При формировании оглавления учитываются только `section`, `point` и `subpoint`, созданные по указанным правилам. Неструктурированные строки в оглавление не попадают.
- Для пунктов и подпунктов внутри `structured_table` также может использоваться `number_revisions` по тем же правилам, что и для обычных элементов (см. раздел 2).
